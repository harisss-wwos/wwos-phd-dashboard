WWOS-GSOC PHD Dashboard

Rules & Definitions

Reference for the hierarchy, ticket statuses, resolve types, age colours, SLA, and incident rules used across the dashboard. Reflects the live code.

1. Role Hierarchy

Higher rank = more privilege. Access is gated by atLeast(role). (manager and admin share the same rank.)

RoleRankNotes
user0Base / logged-in.
editor1Can comment / log on tickets ("touched").
admin2Can publish / upload data.
manager2Same access level as admin, but cannot manage users.
owner3Full access (user management, DB health, delete log entries).

2. Ticket Statuses

  • Open / in-queue (OPEN_STATUSES / OPEN_SET): Assigned, Work In Progress, Pending, Researching
  • Resolved (isResolved): Resolved or Closed

3. Resolve / Closure Types

  • Successful — ClosureCode === 'Successful' (counted as "Successful" in Agent Analytics).
  • Immediate / Auto (IMMEDIATE_AUTO): Immediately Resolved, Automatically Closed.
  • AutoSIM resolved — ResolvedByIdentity contains "AutoSIM" (resolved by the bot, not an agent).
  • Agent resolved — resolved by a real agent (the non-AutoSIM remainder).

4. Ticket Age Colours (open tickets only)

  • Green — ≤ 96 hrs (0–4 days)
  • Yellow — 96–168 hrs (4–7 days)
  • Red — 168–240 hrs (7–10 days)
  • Black — > 240 hrs (> 10 days)
  • Purple — Reopened (_reopened flag OR has a ResolvedDate while still open)

5. SLA Rule

  • SLA_HOURS = 240 (10 days). "SLA compliant" = resolution time ≤ 240 hrs from create date. Weekly SLA % is bucketed by resolved date.

6. Repeat / Historical Incidents (HI)

  • HI count parsed from RootCauseDetails via Cnt: N or Historical Incident: N. Repeat incident = HI count > 0.
  • Pet vs non-pet split: pet = RootCause contains "unsecured animal".
  • Incident-type pet special-casing:
    • Immediately Resolved / Automatically Closed + has an assignee → "First Time Pet Incident (Immediately Resolved / No Action Taken)"
    • else has RootCauseDetails → "Pet Incident (HI>0)"
    • else → "Pet Incident (Resolved by AUTO-SIM)"

7. 1st Pet Incident (tracked metric)

A resolved ticket is a "1st Pet incident" when both conditions below hold. The two categories differ only by who resolved it (ResolvedByIdentity).

  • Condition A — ClosureCode is one of:
    • Automatically Closed
    • Immediately Resolved
  • Condition B — RootCause is one of:
    • NOT APPLICABLE/No Further Action Required
    • Unsecured Animal Attack (CX Pet)
    • Unsecured Animal Attack (Non-CX Pet/ Other)
    • Unsecured Animal Evasion (CX Pet)
    • Unsecured Animal Evasion (Non-CX Pet/ Other)
  • 1st Pet incident (handled by PHD) — Condition A & B, and ResolvedByIdentity is one of our registered agent logins. Attributed to that agent (shown on their profile) and summed into the team total on Agent Analytics.
  • 1st Pet incident (handled by AUTO-SIM) — Condition A & B, and ResolvedByIdentity is exactly arn:aws:sts::511128310777:assumed-role/AutoSIM/AutoSIM. Counted only in the quarter-wide AUTO-SIM total on Agent Analytics.

8. Time Windows (Agent Analytics / Last-24)

  • Resolved 12h / 24h — resolved within the last 12 / 24 hrs relative to now.
  • Crossing 240h next 24h — open tickets currently aged 216–240 hrs.

9. Nav Rail (left-hand icon rail, every page)

The left rail is built by topbar-auth.js and has three zones: the Home logo pinned to the top, the Active Dashboard button pinned to the bottom, and the navigation icon group centered between them.

  • Icons show only when logged in, centered — every middle nav icon is login-gated. Logged-out guests see only the Home logo and the Active Dashboard button; the Reports and Program History fly-outs and the Analytics button are hidden entirely (not just greyed).
  • Home button (top) — links to index.html; styled in light theme (white circle, light border, orange hover).
  • Active Dashboard (bottom) — links to the live quarter dashboard (app.html); styled in light theme (light-green surface with a soft glow). Greyed and inert when logged out.
  • Access gating — Upload requires the canUpload flag; other items are gated by role (user / admin / owner) or per-page flags (sla, sr, repeat, unique). When logged in but lacking access, an item shows greyed and inert rather than hidden.
  • Analytics — admin-gated: clickable for admins, greyed and inert for everyone else.
  • Fixed order — rail order is fixed (drag-and-drop reordering was removed).
  • Right rail — a mirror of the left rail used only on pages without the profile panel; on app.html the right profile panel replaces it.

10. Profile Column (right-hand panel, every page)

The right profile column is built by topbar-auth.js and appears on every page (like the nav rail), on pages that opt into the 3-column layout. When logged out it shows a guest banner with an inline login form instead.

Sections & their data requests (each has its own reload button in the top-right corner that force-refreshes only that section):

  • a) Avatar / banner — /api/me/profile (display name + stored avatar image). Painted from cache first, then repainted with the real photo once the profile loads.
  • b) My open tickets — /api/profile-stats (Assigned / WIP / Researching / Pending).
  • c) My tickets by age — same /api/profile-stats call (Purple / Black / Red / Yellow / Green). Reloading b or c refreshes both, since they share one request.
  • d) Change in data due to last upload — /api/last-upload.
  • e) Agents activity — Today — /api/agents-activity?window=today.
  • f) Agents activity — Yesterday — /api/agents-activity?window=yesterday.
  • g) Agents activity — Last week — /api/agents-activity?window=lastweek.

Caching rules (so the column doesn't re-request on every page):

  • Fetch once, cache across pages — each section's response is cached in localStorage, keyed per user. On navigation (clicking a link or a browser refresh) the column paints from cache with no network call, so the UI stays unchanged and instant.
  • How to get fresh data — either click a section's reload button (force-refreshes just that section), or trigger a full data upload, which clears the profile cache and reloads the page so every section refetches.
  • Cache lifetimes (TTL) — open tickets, tickets-by-age, and last-upload are cached for 6 hours (they only change on upload); the three agents-activity windows use a short 7-minute TTL because a day boundary flips the Today / Yesterday labels.
  • On upload — a successful publish clears the profile cache (PHDClearProfileCache) so the post-upload page reload shows current numbers in every section.

11. Eras (BC / AC — replacing the quarter concept)

An era is a fixed date range based on a ticket's CreateDate. It is replacing the old per-quarter view: a new quarter or calendar year rolls over with no code changes, because the boundary is a fixed date, not a sliding quarter.

EraRange (by CreateDate)Meaning
BC era1 Jan 2021 – 31 Dec 2025Historical, frozen data.
AC era1 Jan 2026 onwardCurrent / active data. The Active Dashboard reads AC.
  • The era is derived purely from CreateDate — nothing is stored on the ticket. Aggregations filter by the date range (AC = CreateDate ≥ 2026-01-01; BC = 2021-01-01 ≤ CreateDate < 2026-01-01), with no quarter filter.
  • Active Dashboard = AC era. Its sections count every 2026+ ticket, independent of any quarter.
  • Queue Status Data (AC era) shows only the open / active work: In Queue, Assigned, Work In Progress, Researching, Pending. Resolved, Closed and Total Tickets were removed from this section (they span the whole era and aren't part of the live queue). Each active status's % is relative to In Queue.
  • Ticket Age Classification (AC era) classifies all open AC-era tickets by age colour (Purple / Black / Red / Yellow / Green), always computed live against the current clock.

12. Performance Overview (Active Dashboard — period picker)

The old Average Data and Weekly Volume & SLA Compliance sections are merged into one Performance Overview card. It holds the resolution / SLA / AutoSIM / repeat KPIs and the weekly Created-vs-Resolved + SLA% chart, both driven by a single period picker. The old Q3 / Q2 / Q2+Q3 scope chips are gone.

Every period is a date range on CreateDate (half-open: ≥ from, < to). Weeks run Sunday–Saturday. Six range types:

OptionWindow
From 1 Jan 2026 (default)AC era to date (CreateDate ≥ 2026-01-01).
By monthA chosen 2026 month (Jan … current month).
By weekA Sun–Sat week within a chosen 2026 month.
Last 100 daysThe 100 days ending today.
Last 12 weeksThe 12 most recent full Sun–Sat weeks.
By quarterA 2026 quarter (Q1 … current quarter).
  • The picker is two levels: a range-type dropdown, plus a second dropdown (month / week / quarter) that appears only when the type needs one.
  • Changing the period reloads both the KPIs and the weekly chart together, scoped to the chosen window — no quarter concept involved.
  • Because the boundary is a date, a new quarter or calendar year needs no code change — the options extend automatically (e.g. the Month / Quarter lists grow as 2026 progresses).
